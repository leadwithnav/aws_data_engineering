Module 1: Multi-Tenancy Architecture & Principles

Building Secure, Isolated, and Resource-Capped Multi-Tenant Kubernetes Clusters.

💡 Learning Objective

Master the pillars of Kubernetes multi-tenancy: Namespaces (logical boundaries), ResourceQuota (aggregate CPU/Memory caps), and LimitRange (default container request/limit injection & min/max bounds).

Multi-Tenancy Building Blocks Comparison

Pillar Kubernetes Object Primary Purpose Key Features
1. Scope Namespace Logical separation of teams, environments, or students. Isolates object names and provides scoping boundary.
2. Quota ResourceQuota Caps aggregate resource consumption across an entire namespace. Prevents noisy-neighbor cluster exhaustion (Total CPU, RAM, Pod count).
3. Defaults LimitRange Injects default container requests/limits and enforces min/max size bounds. Guarantees every pod specifies CPU/Memory requests automatically.

Module 2: 1. Multi-Tenant Namespaces

Creating isolated virtual environments for development, staging, and production teams.

1. Why Use Namespaces?

Namespaces divide a single physical Kubernetes cluster into virtual sub-clusters. They ensure resource naming uniqueness and serve as the binding scope for resource quotas.

2. Namespace Definition Manifest (`namespaces.yaml`)

YAML Manifest (namespaces.yaml)
apiVersion: v1
kind: Namespace
metadata:
  name: analytics-dev
  labels:
    environment: development
    team: data-analytics
---
apiVersion: v1
kind: Namespace
metadata:
  name: analytics-prod
  labels:
    environment: production
    team: data-analytics

3. Execute & Test Namespace Commands (`kubectl`)

Create the isolated namespace, deploy a test workload inside it, and verify cross-namespace isolation:

PowerShell CLI
# 1. Create the isolated development namespace
kubectl create namespace analytics-dev

# 2. Deploy a test pod inside analytics-dev namespace
kubectl run dev-nginx --image=nginx:alpine -n analytics-dev

# 3. Verify pod status inside analytics-dev
kubectl get pods -n analytics-dev

# 4. Verify isolation (pod is NOT visible in default namespace)
kubectl get pods -n default
Terminal CLI

Module 3: 2. Namespace ResourceQuota

Capping aggregate CPU, Memory, and Pod counts to prevent noisy-neighbor cluster exhaustion.

1. What ResourceQuota Controls

A ResourceQuota sets aggregate resource consumption limits for an entire namespace. When total requested CPU or RAM reaches the quota ceiling, any new pod creation is rejected with an HTTP 403 Forbidden error.

2. ResourceQuota Manifest (`resource-quota.yaml`)

YAML Manifest (resource-quota.yaml)
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: analytics-dev
spec:
  hard:
    requests.cpu: "2"         # Max 2 vCPUs total requested in namespace
    requests.memory: "2Gi"     # Max 2 GB RAM total requested in namespace
    limits.cpu: "4"           # Max 4 vCPUs limit ceiling
    limits.memory: "4Gi"       # Max 4 GB RAM limit ceiling
    pods: "5"                  # Max 5 pods total in namespace

3. Execute & Test ResourceQuota Commands (`kubectl`)

Apply the ResourceQuota, deploy a valid pod fitting inside quota, and test quota breach rejection:

PowerShell CLI
# 1. Apply ResourceQuota manifest
kubectl apply -f resource-quota.yaml -n analytics-dev

# 2. Describe ResourceQuota consumption
kubectl describe resourcequota dev-quota -n analytics-dev

# 3. Deploy valid pod fitting within quota
kubectl run valid-pod --image=nginx:alpine --requests="cpu=200m,memory=256Mi" -n analytics-dev

# 4. Test Quota Breach Rejection (Requesting 10 vCPUs exceeds quota)
kubectl run giant-pod --image=nginx:alpine --requests="cpu=10" -n analytics-dev
# Expected Output: Error from server (Forbidden): pods "giant-pod" is forbidden: exceeded quota: dev-quota
Terminal CLI
# 1. Apply ResourceQuota manifest
kubectl apply -f resource-quota.yaml -n analytics-dev

# 2. Describe ResourceQuota consumption
kubectl describe resourcequota dev-quota -n analytics-dev

Module 4: 3. Container LimitRange

Automatic default container CPU/RAM injection and min/max container size boundary enforcement.

1. Why LimitRange is Essential

When a ResourceQuota is applied to a namespace, Kubernetes requires every container to specify explicit CPU and Memory requests. A LimitRange automatically injects default request and limit values if a developer omits them in their pod spec.

2. LimitRange Manifest (`limit-range.yaml`)

YAML Manifest (limit-range.yaml)
apiVersion: v1
kind: LimitRange
metadata:
  name: dev-limit-range
  namespace: analytics-dev
spec:
  limits:
    - type: Container
      default:
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "2"
        memory: "2Gi"
      min:
        cpu: "50m"
        memory: "64Mi"

3. Execute & Test LimitRange Commands (`kubectl`)

Apply the LimitRange, deploy an unconfigured pod without resource specs, and verify default request injection:

PowerShell CLI
# 1. Apply LimitRange manifest
kubectl apply -f limit-range.yaml -n analytics-dev

# 2. Describe LimitRange rules
kubectl describe limitrange dev-limit-range -n analytics-dev

# 3. Test Default Injection: Deploy pod WITHOUT explicit resource requests
kubectl run auto-injected-pod --image=nginx:alpine -n analytics-dev

# 4. Inspect pod spec to verify LimitRange injected 100m CPU / 128Mi RAM requests
kubectl get pod auto-injected-pod -n analytics-dev -o yaml | Select-String "cpu:" -Context 0,2
Terminal CLI
# 1. Apply LimitRange manifest
kubectl apply -f limit-range.yaml -n analytics-dev

# 2. Describe LimitRange rules
kubectl describe limitrange dev-limit-range -n analytics-dev

# 3. Test Default Injection: Deploy pod WITHOUT explicit resource requests
kubectl run auto-injected-pod --image=nginx:alpine -n analytics-dev

# 4. Inspect pod spec to verify LimitRange injected 100m CPU / 128Mi RAM requests
kubectl get pod auto-injected-pod -n analytics-dev -o yaml | grep -A 3 "requests:"
  • Apply & Test LimitRange Default Injection Apply LimitRange, deploy auto-injected-pod, and inspect pod spec for injected CPU/RAM defaults.
