Module 1: Multi-Tenancy Architecture & Principles

Building Secure, Isolated, and Resource-Capped Multi-Tenant Kubernetes Clusters.

💡 Learning Objective

Master the four pillars of Kubernetes multi-tenancy: Namespaces (logical boundaries), RBAC (access permissions), ResourceQuota (aggregate CPU/Memory caps), and LimitRange (default container request/limit injection & min/max bounds).

Multi-Tenancy Building Blocks Comparison

Pillar Kubernetes Object Primary Purpose Key Features
1. Scope Namespace Logical separation of teams, environments, or students. Isolates object names and provides scoping boundary.
2. Security Role & RoleBinding Role-Based Access Control granting specific user/service permissions. Restricts verbs (get, create, delete) on resources per namespace.
3. Quota ResourceQuota Caps aggregate resource consumption across an entire namespace. Prevents noisy-neighbor cluster exhaustion (Total CPU, RAM, Pod count).
4. Defaults LimitRange Injects default container requests/limits and enforces min/max size bounds. Guarantees every pod specifies CPU/Memory requests automatically.

Module 2: 1. Multi-Tenant Namespaces

Creating isolated virtual environments for development, staging, and production teams.

1. Why Use Namespaces?

Namespaces divide a single physical Kubernetes cluster into virtual sub-clusters. They ensure resource naming uniqueness and serve as the binding scope for RBAC policies and resource quotas.

2. Namespace Definition Manifest (`namespaces.yaml`)

YAML Manifest (namespaces.yaml)
apiVersion: v1
kind: Namespace
metadata:
  name: analytics-dev
  labels:
    environment: development
    team: data-analytics
---
apiVersion: v1
kind: Namespace
metadata:
  name: analytics-prod
  labels:
    environment: production
    team: data-analytics

Module 3: 2. RBAC Roles & RoleBindings

Granting fine-grained resource permissions to developers and automated service accounts.

1. Role vs ClusterRole

  • Role: Scoped strictly to a single namespace. Defines allowed actions (verbs) on API resources (pods, jobs, services).
  • RoleBinding: Binds a Role to a User, Group, or ServiceAccount within that namespace.

2. Developer RBAC Manifest (`dev-rbac.yaml`)

YAML Manifest (dev-rbac.yaml)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-role
  namespace: analytics-dev
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log", "services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "delete"]
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["get", "list", "create", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-binding
  namespace: analytics-dev
subjects:
  - kind: ServiceAccount
    name: spark-dev-sa
    namespace: analytics-dev
roleRef:
  kind: Role
  name: developer-role
  apiGroup: rbac.authorization.k8s.io

Module 4: 3. Namespace ResourceQuota

Capping aggregate CPU, Memory, and Pod counts to prevent noisy-neighbor cluster exhaustion.

1. What ResourceQuota Controls

A ResourceQuota sets aggregate resource consumption limits for an entire namespace. When total requested CPU or RAM reaches the quota ceiling, any new pod creation is rejected with an HTTP 403 Forbidden error.

2. ResourceQuota Manifest (`resource-quota.yaml`)

YAML Manifest (resource-quota.yaml)
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: analytics-dev
spec:
  hard:
    requests.cpu: "2"         # Max 2 vCPUs total requested in namespace
    requests.memory: "2Gi"     # Max 2 GB RAM total requested in namespace
    limits.cpu: "4"           # Max 4 vCPUs limit ceiling
    limits.memory: "4Gi"       # Max 4 GB RAM limit ceiling
    pods: "5"                  # Max 5 total pods
  • Enforce ResourceQuota Limits Understand aggregate namespace resource capping across CPU, Memory, and Pod counts.

Module 5: 4. Container LimitRange

Automatically injecting default CPU/RAM requests and setting min/max container size constraints.

1. Why LimitRange is Essential

If a namespace has a ResourceQuota, Kubernetes requires **every single container** to specify resource requests. A LimitRange automatically injects default CPU and Memory requests into any pod manifest that omits them, preventing pod rejection!

2. LimitRange Manifest (`limit-range.yaml`)

YAML Manifest (limit-range.yaml)
apiVersion: v1
kind: LimitRange
metadata:
  name: dev-limit-range
  namespace: analytics-dev
spec:
  limits:
    - type: Container
      default:                # Default Limit if omitted
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:         # Default Request if omitted
        cpu: "100m"
        memory: "128Mi"
      max:                    # Maximum allowed single container size
        cpu: "2"
        memory: "2Gi"
      min:                    # Minimum allowed single container size
        cpu: "50m"
        memory: "64Mi"

Module 6: 5. Minikube Hands-On Verification Lab

Executing step-by-step minikube and kubectl commands to test multi-tenancy enforcement.

Step-by-Step Hands-On Command Suite

PowerShell CLI
# 1. Start Minikube cluster
minikube start --cpus 2 --memory 4096

# 2. Create isolated namespace
kubectl create namespace analytics-dev

# 3. Apply ResourceQuota manifest
kubectl apply -f resource-quota.yaml -n analytics-dev

# 4. Apply LimitRange manifest
kubectl apply -f limit-range.yaml -n analytics-dev

# 5. Verify active quotas and limits
kubectl get resourcequota,limitrange -n analytics-dev

# 6. Test Default Injection: Deploy pod without explicit resource requests
kubectl run test-pod --image=nginx:alpine -n analytics-dev

# 7. Inspect pod spec to verify LimitRange injected 100m CPU / 128Mi RAM requests
kubectl get pod test-pod -n analytics-dev -o yaml | Select-String "cpu:" -Context 0,2

# 8. Test Quota Breach: Deploy pod requesting 10 vCPUs (Exceeds 2 vCPU quota)
kubectl run giant-pod --image=nginx:alpine --requests="cpu=10" -n analytics-dev
# Expected Output: Error from server (Forbidden): pods "giant-pod" is forbidden: exceeded quota: dev-quota
