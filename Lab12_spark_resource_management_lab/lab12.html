Module 2: Layer 1 — Apache Spark Engine

Deciding how many executors are needed via Static vs Dynamic Allocation.

1. What Spark Manages

Apache Spark is the application engine. It evaluates the RDD / DataFrame DAG lineage, calculates stage dependencies, and determines how many parallel executor instances are needed to process data partitions.

  • Static Allocation: User specifies a fixed number of executors (e.g. spark.executor.instances=2).
  • Dynamic Allocation: Spark dynamically requests or deallocates executor pods based on pending RDD tasks in the queue.

2. Spark Dynamic Allocation Configuration

Spark Configurations
# Enable Spark Dynamic Allocation on Kubernetes
--conf spark.dynamicAllocation.enabled=true \
--conf spark.dynamicAllocation.shuffleTracking.enabled=true \
--conf spark.dynamicAllocation.minExecutors=1 \
--conf spark.dynamicAllocation.maxExecutors=10 \
--conf spark.dynamicAllocation.initialExecutors=2
  • Understand Layer 1 (Spark Engine) Recognize that Spark determines executor pod demand, but does NOT schedule pods or manage EC2 instances.

Module 3: Layer 2 — EMR Virtual Cluster

Enforcing logical multi-tenant boundaries and namespace resource quotas.

1. What EMR Virtual Clusters Manage

An EMR Virtual Cluster is NOT a set of EC2 instances! It is a logical abstraction mapped to a single Kubernetes namespace. It enforces multi-tenant security boundaries, binds IAM execution roles, and applies resource quotas.

💡 Key Takeaway

An EMR Virtual Cluster does not provision EC2 nodes. It restricts the maximum CPU/Memory that a student or team can consume inside their assigned Kubernetes namespace.

2. Enforcing Namespace ResourceQuota in Kubernetes

YAML Manifest (quota.yaml)
apiVersion: v1
kind: ResourceQuota
metadata:
  name: student-quota
  namespace: student-01
spec:
  hard:
    requests.cpu: "4"      # Maximum 4 vCPUs per student namespace
    requests.memory: "16Gi"  # Maximum 16 GB RAM per student namespace
    pods: "10"               # Maximum 10 total pods
  • Understand Layer 2 (EMR Virtual Cluster) Verify that EMR Virtual Clusters map 1-to-1 to Kubernetes namespaces and set logical quota boundaries.

Module 4: Layer 3 — Kubernetes Scheduler

Matching Driver and Executor Pod requests against node allocatable CPU and RAM.

1. What Kubernetes Manages

The Kubernetes kube-scheduler receives pod creation requests from Spark Driver and places Driver and Executor pods onto suitable EC2 worker nodes that have sufficient allocatable CPU and Memory.

2. Pod Request Math vs Node Allocatable

⚠️ Why Insufficient CPU Happens

If Driver requests 1.0 vCPU and Executor requests 1.0 vCPU (Total: 2.0 vCPUs), a 1-node t3.medium cluster (2 vCPUs total, but only 1.5 vCPUs allocatable due to system pods) will place the pod in Pending with FailedScheduling: 0/1 nodes available: Insufficient cpu.

3. Configuring Fractional K8s CPU Requests

Use 100m (0.1 vCPU) or 500m (0.5 vCPU) requests to allow multiple pods on smaller nodes:

Spark & K8s Fractional CPU Configs
# Request fractional CPU (100m = 0.1 vCPU per pod)
--conf spark.kubernetes.driver.request.cores=100m \
--conf spark.kubernetes.executor.request.cores=100m \
--conf spark.driver.memory=512m \
--conf spark.executor.memory=512m
  • Understand Layer 3 (Kubernetes Scheduler) Master how kube-scheduler evaluates pod CPU/memory requests against node capacity.

Module 5: Layer 4 — Cluster Autoscaler & Karpenter

Automatically provisioning or terminating EC2 instances based on unschedulable Pending pods.

1. What Cluster Autoscaler & Karpenter Manage

When Kubernetes kube-scheduler cannot find any node with enough free CPU or memory for a pod, the pod enters Pending state. Cluster Autoscaler or Karpenter listens for Pending pods and calls the AWS EC2 API to launch new EC2 instances.

Autoscaler Technology How It Scales Nodes Provisioning Speed
Kubernetes Cluster Autoscaler Scales pre-defined AWS EC2 Auto Scaling Groups (ASGs). ~3 to 5 minutes
Karpenter (Modern EKS Native) Bypasses ASGs; directly launches optimal EC2 instances matching exact pod constraints. ~45 to 60 seconds

2. Karpenter NodePool Specification (`nodepool.yaml`)

YAML Manifest (nodepool.yaml)
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: spark-node-pool
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand", "spot"]
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["m5.xlarge", "m6i.xlarge", "c5.xlarge"]
  limits:
    cpu: "100"  # Total cluster scaling limit across all EC2 nodes
  • Understand Layer 4 (Autoscaler / Karpenter) Learn how Karpenter monitors Pending pods and provisions new EC2 instances automatically.

Module 6: Layer 5 — EC2 Compute Nodes

Providing physical hardware CPU cores, RAM, and EBS volume storage.

1. What EC2 Nodes Manage

EC2 Compute Nodes (e.g. m5.xlarge) are the underlying infrastructure hardware. They host the Linux kernel, contain Docker / containerd container runtimes, and provide physical CPU cycles, memory pages, and EBS disk I/O.

2. Node Capacity vs Allocatable Math

A node's total hardware capacity is reduced by Kubernetes system reserves before pods can be scheduled:

Formula
[Node Allocatable] = [Total Hardware Capacity] - [kube-reserved] - [system-reserved] - [eviction-threshold]

Example (m5.xlarge - 4 vCPUs, 16 GB RAM):
Total Capacity : 4000m CPU, 16384 MiB RAM
Reserved System: 150m CPU,  1200 MiB RAM
Allocatable    : 3850m CPU, 15184 MiB RAM

3. Inspecting Node Capacity via `kubectl`

Kubectl CLI
# View allocatable CPU and Memory for all nodes
kubectl describe nodes | grep -A 6 "Allocatable:"
  • Understand Layer 5 (EC2 Nodes) Verify allocatable capacity math and how system pods reserve CPU/RAM on worker nodes.
