Module 1: Overview & Concepts

Adaptive Partition Coalescing, Dynamic Planning, and Exchange Reuse in Spark 3.x.

💡 Learning Objective

Build a deep conceptual and visual understanding of Spark Adaptive Query Execution (AQE). Learn how Spark dynamically optimizes query physical plans at runtime by re-evaluating shuffle stats after each stage completes.

Why Adaptive Query Execution (AQE)?

In traditional query execution, Spark builds a static physical plan based on estimated table statistics before execution begins. However, data skew, inaccurate file stats, and complex filters often lead to sub-optimal plans. AQE bridges this gap by modifying execution plans dynamically during query execution.

Core AQE Mechanisms

  • Dynamic Partition Coalescing: Merges tiny shuffle partitions into larger partitions to avoid launching hundreds of redundant tasks.
  • Dynamic Join Selection: Automatically converts a SortMergeJoin to a BroadcastHashJoin if a table's actual runtime size falls below the broadcast threshold.
  • Dynamic Skew Join Optimization: Detects skewed partitions at runtime and splits them into smaller sub-partitions.
  • Exchange Reuse: Caches intermediate shuffle outputs to skip redundant stage execution across query branches.

Module 2: Dynamic Partition Coalescing

Consolidating tiny shuffle partitions to eliminate scheduling overhead.

The Small Partition Problem

By default, Spark sets spark.sql.shuffle.partitions = 200. When performing wide transformations on smaller datasets, Spark launches 200 reducer tasks—most of which handle only a few kilobytes of data. Launching 200 tasks incurs heavy CPU scheduling and task creation latency.

How AQE Coalesces Partitions

When AQE is enabled (spark.sql.adaptive.enabled = true), Spark measures the actual written byte sizes of shuffle partitions after Stage 0 completes. If multiple adjacent partitions fall below spark.sql.adaptive.advisoryPartitionSizeInBytes (default 64 MB), AQE automatically coalesces them into a single reducer task.

Module 3: One Job Per Stage Execution

Understanding why AQE triggers separate Spark Jobs for individual stages.

⚠️ Key UI Difference in AQE

With AQE enabled, executing a single DataFrame action triggers multiple Job IDs in the Spark UI. Each shuffle stage is submitted as its own independent Job so Spark can inspect stats before planning the next stage.

AQE Stage Materialization Workflow

  1. Spark submits Stage 0 as an independent Job.
  2. Worker nodes write intermediate shuffle output files to disk.
  3. Driver inspects shuffle stats (bytes written, row counts per partition).
  4. AQE dynamically re-plans downstream operations (coalescing, skew join, broadcast join).
  5. Spark submits Stage 1 as a new Job consuming the materialized shuffle files.
  • Observe Multi-Job Submission Recognize how AQE breaks query actions into stage-by-stage job submissions in Spark UI.

Module 4: Exchange Reuse & Skipped Stages

Reusing computed shuffle files across query branches to skip redundant work.

Reusing Computed Exchanges

When multiple queries or subqueries perform identical shuffle operations (e.g. joining or grouping on the same key), AQE detects the duplicate exchange operator. Because intermediate shuffle files are already written to disk during earlier stage execution, Spark reuses the computed shuffle data directly instead of re-reading source files.

Identifying Skipped Stages in Spark UI

In the Spark UI Jobs & Stages DAG view, reused exchanges appear as light blue/grey "skipped" stages. This indicates that Spark skipped re-executing the map-side stage because valid shuffle files already exist on disk.
